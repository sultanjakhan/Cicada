# Personal native-task file import

Review branch from accepted `d445160c74dee3e8f2016fe47d662cf9182130cc`. Not installed; no production import performed.

The existing Settings → Calendar panel has one collapsed file-import action. This is separate from the published work registry. It writes the existing native Tasks using `create_note(status: task)`, revision-checked `update_note`, and `get_note` readback. No timer, execution, model call, new server, external CLI or credential is introduced. Normal application sync behaviour is unchanged.

Input: UTF-8 JSON, at most 64 KiB; exact fields `schemaVersion: 1`, `kind: personal-native-tasks`, `namespace: personal-backlog`, `tasks`, `archiveTemplates`. Task fields: `externalId`, `title`, `projects`, `status`, `operation`, `waitingFor`, `result`, `dependsOn`. IDs are stable lowercase slugs; duplicate keys (including escaped spellings), duplicate IDs, unknown fields/statuses/projects, unknown/cyclic dependencies and oversized input fail closed. Maximum 100 tasks, 50 explicit archive IDs. Supported plan statuses: planned, waiting, decision-needed. They remain descriptions, not agent execution or native completion.

Mapping: one task per external ID, including shared Cicada + Agent City work. New records are explicitly personal (`task-sphere:personal`). Later user-owned non-work sphere changes are preserved. Project tokens are `project:cicada`/`project:agent-city`, ordinary tags, not a new native project relationship or goal. A task with no projects gets no project tags. Operation, waiting, result and dependencies are preserved as readable description; this version creates neither native dependency edges nor a new goal record. It does not force a task process/stage just to display waiting. Native Tasks expose the imported titles; description and custom tags are stored in the existing record.

Preview performs only scoped reads. The existing get_notes API has a narrowly validated `personal-import` filter: exact namespace/marker, including archived/completed own imports. Matching IDs are checked using scope metadata before content loads. Changing a personal sphere cannot hide identity; work/unknown/Jira/InvestLink scope conflicts before loading content. General tasks/Jira/InvestLink are not enumerated. Existing non-imported tasks are never merged by title. Duplicate own markers or archived/completed own records produce a conflict, not a new record. One apply runs at a time in the application module. Native create additionally uses BEGIN IMMEDIATE to atomically check the stable marker and insert, serializing different connections to the same SQLite database. Cross-device independent databases/out-of-band replication are not a new distributed uniqueness protocol. Stable marker is stored in tags, while the description uses readable plan-status labels; a lost create response can be recovered by a fresh preview without another create.

Before apply, the user saves and acknowledges a verified native personal before-image/export. Apply revalidates the entire preview, calls existing create_backup, persists the prepared recovery receipt before mutations, then performs per-record revision checks and readback. Each recovery phase and the final report are saved in the application-owned backups directory with exact byte readback and SHA-256. A failed save aborts dependent writes and remains visible. Interrupted runs require a fresh preview. Backup path and before-images support reviewed recovery; no automatic destructive rollback or direct SQL is offered.

Archives are a separate final phase after task creation/readback. Input items require exact UUID `id`, positive `expectedVersion`, and `personalTemplateConfirmed: true`. Only these explicitly declared personal IDs are considered; there is no template discovery or bulk removal. get_note(personalOnly: true) checks scope metadata before loading title/content: a positive non-work sphere or personal-template token is required, and work/Jira/InvestLink/import markers are rejected. Ambiguous untagged templates remain untouched. Work/Jira/InvestLink/imported-task tokens, archived/completed records and stale revisions are rejected. Export happens first; archive uses update_note(archived: true, expectedVersion), preserving title/content/tags and other fields. A partial archive that already succeeded requires reviewing the report and removing/updating the corresponding explicit request before retry; it is never toggled back automatically.

Synthetic JS domain tests cover strict input, own-only reads, project mapping, backup/export failure, lost response retry, update conflicts, duplicate/archived markers, explicit archive/export/readback and recovery plans. Rust MockRuntime tests exercise actual Tauri deserialization/SQLite domain queries and revision protection; they are not native-window evidence. Headless UI tests and builds also do not imply native acceptance. Independent review and isolated native acceptance are required before a release/install or personal production import.

It accepts report JSON only (kind/version + 8 MiB cap), no destination path, reserves a unique .json file, flushes, closes and reads back exact bytes, then returns verified/path/SHA256/byte count. Direct backup-directory symlinks/reparse points are rejected. The existing native app/isolated root policy is retained; no generic filesystem permission, plugin, shell, network, credential or directory migration is added.
