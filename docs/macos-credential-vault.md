# Подключения без платной подписи Apple

Владелец выбрал этот вариант 28.09.2026. Обычная замена Cicada не должна
требовать повторного ввода Jira-токена и ключа синхронизации. База, профиль,
этапы и время остаются прежними.

## Причина и устройство

Прежняя Cicada обращается к файловой Keychain своим исполняемым файлом.
У ad-hoc сборки меняется CDHash; macOS перестаёт предоставлять новой сборке
доступ к записи старой. Копирование базы или файла приложения этого не исправляет.

Новый `cicada-vault` владеет двумя отдельными Keychain services: Jira и relay.
Его точный подписанный бинарный файл хранится вне `.app`, в
`~/Library/Application Support/app.hanni.mvp/vault/v1/`. Обычное обновление
интерфейса его не заменяет и не пересобирает. Публичные разрешения сборок
лежат в `vault/proofs/<CDHash>.json`; токенов там нет.

Каждая сборка получает разрешение, подписанное существующим ключом выпуска
Minisign. Разрешение содержит назначение, версию протокола, приложение,
архитектуру, версию, CDHash клиента и ожидаемый CDHash хранилища.
Закрытый ключ выпуска остаётся в CI, в приложение и хранилище входит только
публичный ключ. Имя процесса, bundle ID или владение пользовательским каталогом
сами по себе не дают доступа.

Обмен идёт через XPC. Первое сообщение содержит только публичное разрешение.
После проверки идентичности ответившего процесса клиент получает anonymous
endpoint: при обрыве он не переключится на подменённый именованный сервис.
Каждый запрос проверяется через `SecCodeCreateWithXPCMessage` и точный CDHash
из проверенного разрешения. Обе стороны требуют hardened runtime без исключений
для внедрения кода. Проверка по PID или `LOCAL_PEERTOKEN` не используется.

Хранилище принимает только операции с двумя собственными services и account,
полученным из хеша канонического пути базы. Произвольных путей экспорта,
имён Keychain services и сетевого интерфейса нет. Секреты не попадают
в JavaScript, журнал или Git. Ошибка доступа остаётся ошибкой доступа,
а не отсутствующим токеном.

Запись считается успешной после чтения и сравнения. Повторная запись безопасна
после таймаута; таймаут сам по себе не доказывает отмену операции. Отключение
оставляет пустую запись, запрещающую восстановление прежнего токена из старой
Keychain. Native-вызовы выполняются через существующие фоновые IPC-обработчики.

## Обновление и первый переход

Сборка с `CICADA_VAULT_CDHASH` обращается к закреплённому хранилищу. Перед
обновлением проверяются нынешний доступ к обоим подключениям, подпись архива,
разрешение и native-подпись кандидата, версия и неизменность хранилища.
Разрешение новой сборки сохраняется отдельно до замены `.app`; старое
разрешение остаётся для отката. Копия SQLite и прежнего приложения по-прежнему
нужна: хранилище решает доступ к ключам, а не совместимость миграций базы.

Если новая сборка ещё может прочитать прежний ключ, она переносит его через
защищённый канал и проверяет сохранение. Недоступный старый ключ не извлекается
обходом ACL. **Автоматический перенос нынешнего production-токена со старой
сборки не подтверждён.** Возможный однократный ввод при переходе согласуется
отдельно после готовности кандидата; рабочую Cicada пока не заменяют.

Замена самого хранилища — отдельная миграция. Упаковка закрепляет его SHA-256
и CDHash, установщик отказывается перезаписывать другой helper, а обновление
отклоняет кандидата с другим helper CDHash. Нельзя решать будущую миграцию
разрешением чтения Keychain всем приложениям.

## Воспроизведение и выпуск

`python3 scripts/test-macos-vault.py` создаёт отдельную временную связку,
искусственный ключ выпуска и временный LaunchAgent. Две разные native-сборки
читают одни сохранённые вымышленные данные Jira и relay через неизменный helper.
Проверяются перезапуск, откат к первому клиенту, задержанный ответ, отключение
и повторное подключение; чужой клиент с копией разрешения, изменённая подпись,
поддельный helper и прямое чтение Keychain получают отказ. В конце удаляются
тестовая связка и LaunchAgent; login Keychain, её ACL и production не изменяются.

Первый артефакт создаётся явно:

```sh
python3 scripts/macos_vault_package.py --freeze .local/macos-vault/v1
```

После проверки исходников и бинарного файла его `release.json` закрепляется
в `native/macos-vault/release.json`. Один и тот же артефакт сохраняется для CI;
поле `url` указывает на его неизменяемый release asset. До публикации можно
использовать `MVP_MACOS_VAULT_BINARY` с обязательной проверкой того же SHA-256.
Обычная сборка не создаёт новый helper. Для app и разрешения используются
`scripts/package-update.py macos` и существующий ключ выпуска в CI.

`scripts/prepare-macos-vault.py --bundle <кандидат.app> --proof <vault-proof.json>`
проверяет обе идентичности и подпись разрешения, устанавливает только helper,
его LaunchAgent и публичное разрешение. Она не заменяет приложение, не читает
токены и не подтверждает миграцию. Запуск установленной Cicada, реальный обмен,
сохранность базы и второе обновление проверяются отдельно.

На момент подготовки реализации подтверждены синтетические native-сценарии.
Подписанный release-кандидат, первый перенос production и полный переход
между двумя установленными Cicada ещё не приняты.

API: [проверка отправителя XPC](https://developer.apple.com/documentation/security/seccodecreatewithxpcmessage(_:_:_:)),
[защита исполняемого кода](https://developer.apple.com/documentation/security/hardened-runtime).

Проверенный артефакт v1 закреплён в репозитории; URL в pin — назначение
для будущей публикации, не свидетельство уже выполненного выпуска. Локальный
артефакт находится в `.local/macos-vault/accepted-v1/cicada-vault`.
