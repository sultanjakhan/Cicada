# Recurring record version convergence

Для identity `ui / calendar_recurring_v1 / plans|days` версия record v2 имеет приоритет над v1 в обоих направлениях доставки. Более поздний timestamp старого writer не возвращает identity на v1. Между одинаковыми версиями сохраняется существующий порядок `(stamp, writer)`.

Принимается целая выигравшая запись с исходными payload, stamp и writer. Противоречащий ей v1 сохраняется в архиве конфликтов, даже если его timestamp позднее. Идентичный v1 и известный предок v2 не создают лишний конфликт. Tombstones участвуют в том же приоритете версий. Явный выбор v1 в конфликте по прежнему механизму создаёт новую запись v2.

Повтор того же stamp/writer с изменением `v` отклоняется как `content_sync_version_conflict`, даже при одинаковом value. Миграция версии обязана создавать новый stamp. Побайтовый порядок ключей JSON не является идентичностью; поля, значения и stamps сохраняются.

Регрессии `graph_version_convergence_*` используют зашифрованные transport batches и три SQLite-получателя: v2 сначала, v1 сначала и повторная перемешанная доставка. Матрица включает plan/day и live/tombstone для обеих версий. Дополнительно проверяются архив точного losing payload, пустой pending, одинаковое содержимое, известный предок и коллизия stamp.

При объединении с reflection/retention сохранить их независимые приоритеты и guards. Graph version priority относится только к recurring core identity; отдельные reflection и retention records остаются v1. Эта проверка не подтверждает native UI или доставку на физические устройства.
